- [HIGH] src/Application/CatEcommerce.Application/DomainEventHandlers/Account/AuditStaffPasswordSetHandler.cs:28. The audit row does not say who set the password. It writes `ActorUserId: @event.StaffAccountId` (the TARGET) and `Reason: "PasswordReset"`/"FirstPassword". Until this commit only the staff member's own reset raised this event. Now an administrator raises it through PUT /api/staff-accounts/{id}/password and through POST /api/staff-accounts with a password. The audit log view (GetAuditEntriesQueryHandler joins on ActorUserId) therefore says the victim reset their own password, and filtering by the acting administrator finds nothing. Scenario: admin A sets admin B's password and signs in as B. Every later action is recorded as B, and the takeover itself is recorded as B's own reset. The admin's id at most survives in the generic UserContext default columns, which the audit UI does not show. This is the accountability control the commit relies on ("setting it audits"). Fix: carry the acting user in the event (for example `SetByUserId = dto.UserContext.UserId`). When it differs from the target, record `ActorUserId = SetByUserId` and Reason "SetByAdministrator" (and "InitialPasswordByAdministrator" on create). Add a handler test and an endpoint test asserting the actor.
- [MEDIUM] src/Application/CatEcommerce.Application/CommandHandlers/Account/SetStaffPasswordCommandHandler.cs:28-45. There is no step-up re-authentication and no self-target rule. Any Administrator session can set a new password for itself or any other administrator without entering its own current password. The customer side already requires the current password for sensitive self-service changes (Delete account, contact details). A stolen or unattended admin session can therefore lock out every other administrator and turn a session hijack into lasting credentials. Self-targeting works and rotates the caller's own stamp, so the caller is signed out on the next request; this is safe but undocumented and untested. Fix: require the acting administrator's current password on this endpoint (and on create-with-password). Either refuse self-targeting or send it to a change-own-password flow. Backlog it if the owner accepts the risk.
- [LOW] src/Application/CatEcommerce.Application/CommandHandlers/Validators/CreateStaffAccountCommandValidator.cs:24-29 and SetStaffPasswordCommandValidator.cs:12-17. `.MaximumLength(...)` has no WithErrorCode/WithMessage, unlike `PasswordTooShort`.
