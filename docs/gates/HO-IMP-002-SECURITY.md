FINDINGS
- [LOW] web/app/(staff)/staff/inventory/reorder-policies/page.tsx:17,63 and web/app/(staff)/staff/inventory/locations/page.tsx:28. §17 says "actions rendered only from `allowedActions`; no authorization decision in the client". Instead, `canEdit` and `canManage` are worked out from `session.roleIds` (`['Inventory','Administrator']` and `'Administrator'`). Nothing is exposed, because the server still enforces every write. But if the server's role-to-action map changes, the buttons will drift from it: users may see buttons that return 403, or not see actions they are allowed to take. Fix: take a capability flag or `allowedActions` from the locations and reorder-policies payloads, as the batch, PO, consignment, count, adjustment and breach screens already do. Until the server sends one, record the role mirror as an ADR-FE-039-style presentation-only map.
- [LOW] web/lib/api/inventory-recalls.ts:52,62,135,145,150,157 and the other new `lib/api/inventory-*.ts` / `procurement-*.ts` modules. Route-param ids (`batchId`, `consignmentId`, `purchaseOrderId`, `countId`, …) are put into API paths without `encodeURIComponent`. Sibling modules do encode them (`lib/api/cats.ts`, `admin-*.ts`, `booking.ts`). This allows client-side path traversal: a crafted staff link whose id segment decodes to `../../…` sends the GET, and the CSRF-carrying POST behind a confirmed action, to another `/api/**` path. Exploitability is low today. Every mutation screen first needs a successful GET of the same traversed path that returns a correctly shaped entity, and the backend routes use `:guid` constraints. Fix: wrap path ids in `encodeURIComponent`, or reject non-GUID route params before any query runs.
- [LOW] web/components/inventory/ExportLink.tsx and web/lib/hooks/useExportBranchNote.ts (ledger, near-expiry and stock-on-hand CSV). These are plain links, so the server resolves them to the staff member's PRIMARY branch. Meanwhile the query string (for example `locationId`) comes from the ACTIVE branch. At a non-primary branch the file covers a different branch, filtered by a location from another branch, so it is usually empty or misleading. The note under the link says this. There is no confidentiality issue: the server limits the file to a branch the caller belongs to and checks the permission. The recall trace CSV is not branch-scoped, so this does not affect it. Fix (backlog): have the server accept an explicit `branchId` query parameter for `.csv` routes, validated against the caller's branch memberships.
