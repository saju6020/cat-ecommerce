ROUND 1 HIGH: RESOLVED. Reasoning checked:
1. Lock cycle. Advisory locks are taken only in the commit-time flush, ordered by (sku_id, branch_id), after the transaction has taken every row lock it will take. The flush's own writes (summary delete/insert, dirty delete) touch only rows protected by the pair's advisory lock or the transaction's own rows, and its reads of positions/batch/location take no row locks, so a committing transaction never waits on a row lock held by a peer. Wait-for edges therefore run: in-flight writer -> committer (row locks), committer -> committer with a smaller key (advisory). No cycle is possible. A peer's uncommitted position change is invisible to the flush and is picked up by that peer's own flush, which runs after this one under the same pair lock and re-reads committed state under a fresh READ COMMITTED snapshot. (The app uses no REPEATABLE READ/SERIALIZABLE; grep none.)
2. Dirty-table writes. Key is (txid_current(), sku, branch); txids are unique per transaction, so two transactions never insert the same key and cannot deadlock on the unique index, and ON CONFLICT DO NOTHING can only ever see the transaction's own rows.
3. Isolation. Flush reads and deletes WHERE txid = txid_current() only. Rollback and ROLLBACK TO SAVEPOINT discard the marks and queued events together; a mark inside a rolled-back sub-transaction followed by a later change re-inserts a fresh mark. A transaction that rolls back leaves nothing behind. Crash leaves nothing (rows are never committed except by a crash between flush and commit, which rolls back).
4. Constraint trigger. DEFERRABLE INITIALLY DEFERRED, row level, first firing flushes everything and later events find nothing. A failing refresh fails the COMMIT and rolls back the whole write: consistent, nothing half-applied. EF SaveChanges transactions, and statement-level autocommit (each statement is its own transaction), fire the deferred trigger at that commit; no path writes stock outside a transaction, and none uses SET CONSTRAINTS.
