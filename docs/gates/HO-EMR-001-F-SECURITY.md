CHECKED AND SOUND
- Authorisation: all four new actions carry `[RequireAction(Actions.Visits.WriteNote)]` (Vet only). A Nurse or Reception gets 403 on the write and on both dispensary reads (`OnlyAVetRecordsTreatments_AndReadsTheDispensary`).
- Branch scope: the branch comes from `IActiveBranchAccessor` through `TryResolveBranch` (403 when unresolved). Both handlers refuse `visit.BranchId != command.BranchId` with `VisitNotFound` → 404, so a refusal never confirms the visit exists (`AVisitOfAnotherBranch_IsNotFound_ForTreatments`). Reversal uses the same check (TreatmentHandlers.cs:295).
- IDOR, line: the line is looked up only inside the branch-checked visit aggregate (`ReverseTreatment`, `TreatmentLineNotFound`). Stock is returned using the SKU, batch and quantity stored on the line, never values from the request.
- IDOR, batch and location: a named `BatchId` is accepted only if it appears in `DispensaryBatchPicker.ReadAsync(visit.BranchId, sku)`. That list is built from `GetDispensaryBatchesAsync`, which returns only `ClinicDispensary` candidates of that branch, so a batch from another branch, store or quarantine location is `BatchNotIssuable`. The location sent to the ledger comes from that server-side list, never from the client.
- Expired batch and override: the batch's `RefusalCode` (Inventory's `GetBatchUsabilityAsync`) is checked before the override reason, so no reason relaxes an expiry (I-F2). A non-FEFO batch needs a reason of at least 5 characters. The reason is stored on the line (`batch_override_reason`), the ledger entry is flagged `FefoOverridden`, and Inventory adds a BusinessEvent audit row with the before and after plans. The ledger re-plans and re-checks usability at deduction, so a batch that expires or is recalled between the read and the write is still refused.
- Race on the last unit (I-F4): both requests are gated at `DeductAsync`. One gets 201, the other 409, the shelf ends at 0 with one movement, and the losing line is not committed. The line and the movement share one commit (F23), and I-F6 shows a failing ledger insert leaves neither. A concurrent double reversal is also covered: the visit row is `xmin`-guarded (ADR-016), so the second save throws `DbUpdateConcurrencyException` (409) and its return entry rolls back with it. There is no test for this; CODE_REVIEW F row 45 asks for one.
- Shortfall: `AcceptShortfall` cannot bypass the controlled check, the expiry check or the override reason, because all three run before the quantity comparison. The deducted quantity is capped at the batch's free quantity, and the aggregate enforces deducted + shortfall = quantity. The shortfall alert goes to the server-resolved branch dispensary.
- Reversal audit: `TreatmentReversedEvent` writes a BusinessEvent row with `LineId` and `StockReturned` only, never the reason. The line keeps `reversed_by`, `reversed_on` and `reversal_reason`, and is never removed.
- Triggers: `tr_visit_treatment_frozen` (BEFORE INSERT/UPDATE/DELETE, `clinic.visit_child_frozen()` as hardened in 20261009055613) refuses every DELETE, any change of `visit_id`, and any insert or update under a finalised visit. `tr_visit_treatment_no_truncate` refuses TRUNCATE. The `ON DELETE CASCADE` from `clinic.visit` would hit the same DELETE refusal.
- Stock-ledger free text: the reference label is `Visit <12 hex of id> treatment|reversal`, the party is ids only (OwnerId, CatId), and the return note is a constant. The only free text that reaches Inventory is the batch override reason (L2 above).
- Events: `TreatmentRecordedEvent`, `TreatmentReversedEvent` and `ClinicalStockShortfallRecordedEvent` carry ids, kind, flags and quantities only. None carries a description, dose, route, reason or name.
