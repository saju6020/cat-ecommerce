- **Reproduction.** I ran it in a throwaway `git archive` copy against `catecommerce_apt001`. The copy was deleted afterwards and the worktree was not touched. Setup: one customer, one cat, 12 concurrent `POST /api/customers/me/appointment-holds` for 12 different 30-minute slots, repeated for 3 rounds.
  - **HEAD 9af0d22:** 201x12 / 201x12 / 201x11+409x1. There was **exactly 1 live `Held` row after every round**. The single 409 was `SlotNoLongerAvailable`: the request for the slot the customer already held is refused by slot validation, because the cat is busy there. That is a functional quirk, not a security issue.
  - **Negative control on 906cfcc:** 201x12 and **12 live `Held` rows**, the same result the first pass got.
  - The new test `PlaceHold_EightConcurrentRequestsFromOneCustomerForDifferentSlots_AtMostOneHeldRowRemains` and I-C2 (`PlaceHold_TwentyConcurrentRequestsForSameSlot_ExactlyOneSucceeds`) each passed 6 out of 6 runs. The whole `AppointmentBookingFlowTests` class passes (5/5).
- **The lock is parameterised.** `CustomerHoldSerializer.cs:23-24` uses `ExecuteSqlInterpolatedAsync($"... hashtextextended({key}, 0)")`, so `key` is sent as an Npgsql parameter. The key is the server-side `Guid` itself, never request input, so there is no SQL injection.
- **The lock is transaction-scoped and always released.** It is `pg_advisory_xact_lock` inside an explicit `BeginTransactionAsync` on the scoped DbContext. There is no retrying execution strategy (`Program.cs:100`), so a user transaction is allowed. It commits on success and rolls back in the `catch`, and `await using` disposes the transaction in any case. Probes confirmed that `pg_locks` showed 0 advisory locks after the success path, after the 23P01/409 path, and after the timeout path. After a 409, the same customer's next hold succeeded straight away (105 ms total).
- **The lock cannot be held indefinitely.** I held X's key externally and never released it. X's PlaceHold failed after 30.9 s, which is the Npgsql default `CommandTimeout`, and there was no leftover lock. The response is a body-less 500 from `SafeExceptionHandlerMiddleware`. That is acceptable: it can only happen if another transaction holding *the same customer's* key runs for more than 30 s.
- **There is no per-customer DoS.** The key is `hashtextextended(customerId)`: 64-bit, the id is server-generated, and nothing else in `src/` takes an advisory lock, so an attacker cannot target a victim's key. Probe: while customer X's key was held externally, customer Y's hold returned 201 in 51 ms. X's hold did not complete within 4 s, then completed in 21 ms once the lock was released. Contention is limited to the caller's own concurrent requests, and those are capped by the per-customer rate limit (`QueueLimit = 0`).
- **The rate-limit partition cannot be spoofed.** `AppointmentsModule.cs:91-103` reads `ResolvedCaller` from `HttpContext.Items`. Only `SessionAuthenticationMiddleware.cs:129` writes it, after a server-side session-token-hash lookup (`GetCurrentCustomerSessionQuery`). `UseRateLimiter()` runs after `UseAccountsModule()` (`Program.cs:189-197`). No header or body value feeds the key. Anonymous or unresolved callers fall back to `ip:<RemoteIpAddress>`. `RemoteIpAddress` is itself hardened: `ForwardLimit = 1`, known proxies only (`HostPipelineExtensions.cs:61-87`).
- **40P01/I-C2 has not regressed.** Losers of a same-slot race still get `409 SlotNoLongerAvailable`. The exception propagates out of `RunSerializedAsync` after rollback, unchanged. It reaches `UniqueConstraintExceptionFilter` (which unwraps to `DbUpdateException`) on the `[SlotClaimEndpoint]` action.
