VERIFIED (no finding)
- Authorization: all 86 Inventory/Procurement action methods across the 17 new controllers carry `[RequireAction]`, and every action/role pair matches §12.3 exactly (ActionRoles.Inventory.cs).
- Branch scoping: every branch-scoped endpoint resolves `IActiveBranchAccessor` and returns 403 with no branch. Handlers compare the loaded record's BranchId and return 404 for another branch's location, PO, receipt, adjustment, count, transfer, breach or batch. Ledger, stock and report reads filter on BranchId.
- Cross-branch transfer: the source must be in the active branch; a destination in another branch needs a `StaffBranchAssignment` to that branch, otherwise a 404-shaped refusal.
- Adjustment segregation of duties (ADR-107): the value is the sum of |delta| x unit cost, so +X/-X lines cannot net to zero. Above the threshold the adjustment is `PendingApproval` with no ledger entry. The approver must hold `Stock.ApproveAdjustment` (checked again in the handler, `ApproverCheck`) and must differ from the requester. Only the requester can withdraw. A count above the threshold uses the same approval gate.
- Ledger immutability: BEFORE UPDATE/DELETE and TRUNCATE triggers on stock_ledger_entry and stock_reservation_entry. stock_position is written only under the apply-trigger GUC. ck_stock_position_balance (on_hand >= 0, reserved >= 0, reserved <= on_hand) is the commit-time race control, so negative stock and over-reservation are refused by the database.
- Recall and quarantine race: tg_stock_batch_usable is on both entry tables. It reads the batch FOR SHARE and refuses consuming kinds (Sale/Dispense/ClinicalUse/BoardingUse) and Reserve unless the batch is Available and not expired in the branch's local date. `ConsumeReservationAsync` re-checks usability, so a reserved batch that is then recalled cannot be dispatched. No API path relaxes the check.
- Recall trace and CSV: restricted to `Recalls.Manage` (Nurse gets 403). Anonymised customers are shown with no contact details. Merges are resolved at read time. The CSV export writes a `RecallTraceExported` BusinessEvent audit row before the file is returned, and refuses the export if the audit write fails. The CSV writer applies the ADR-051 guard (= + - @, after leading whitespace) to every text cell.
- Ledger CSV: needs `InventoryReports.View`, is branch-scoped, has no customer or cat fields, is capped at LedgerCsvMaxRows (413 above it) and at 366 days.
- PII: ledger and reservation rows hold customer and cat ids only. Audit rows (FEFO override, trace export, register correction) hold ids, quantities and reasons. New log statements log ids only. The erasure exemption (C-ALL-2) is justified because recall resolution happens at read time. Supplier contacts are business contacts with length limits.
- Worker: runs as SystemActors.InventoryWorker with no roles. Raise and resolve alert commands are not reachable over HTTP, and each item is dispatched in its own scope.
- Notifications: the `inventory.batch-recall` template contains no link or URL. `customerAdvice` is staff text with a length limit and no control characters. BatchRecallGuard cancels pending notices once a recall is withdrawn. A deduplication key prevents double sends.
- Migrations: the raw SQL is constant text generated from C# enumerations (InventoryLedgerSql), plus static CREATE/DROP SEQUENCE statements. No user input reaches it.
- Input validation: every command validator sets length limits and NoControlCharacters, and caps line counts (receipt, PO, transfer, adjustment, count, SKUs, HS codes).

FINDINGS
- [MEDIUM] src/Application/CatEcommerce.Application/CommandHandlers/Inventory/BatchStatusCommandHandlers.cs:78-117 — write-off bypasses ADR-107. `WriteOffBatchCommand` needs only `Batches.ManageStatus` (Inventory role) and a reason. It zeroes every position of the batch with Wastage entries, whatever the value, with no threshold and no second approver. An adjustment or count of the same value would wait for a different Administrator. Exploit: an Inventory user writes off a high-value batch alone. This is spec-conformant (§12.3, C9) and every write-off is attributable in the immutable ledger, so it is not a gate failure. Remediation (owner decision): route a write-off whose value is above `inventory.adjustmentApprovalThreshold` through the same PendingApproval/approver-must-differ flow, or restrict write-off to `Stock.ApproveAdjustment`.
- [MEDIUM] src/Application/CatEcommerce.Application/CommandHandlers/Inventory/BatchStatusCommandHandlers.cs:93 — write-off reaches other branches. The batch is scoped by its receiving branch (BatchLoader), but `GetPositionsOfBatchAsync` returns positions at every branch. A user assigned only to branch A can therefore write off stock that was transferred to branch B, creating Wastage entries at B's locations. Transfers require assignment to the other branch; write-off does not. Remediation: limit the Wastage drafts to positions whose location is in a branch the caller is assigned to (and refuse otherwise), or require assignment to every branch holding the batch.
- [MEDIUM] src/Domain/CatEcommerce.Domain/Aggregates/Inventory/StockCountAggregate.cs:153 — count approval only checks the person who committed. The approver is compared with `CommitRequestedBy` alone, not with whoever recorded or submitted the lines. Exploit: Administrator A records a false count and submits it; any Inventory user commits it, sending it to AwaitingApproval; A then approves a variance A wrote. Remediation: also refuse `approverId == SubmittedBy`, and any id in `Lines[].CountedBy`.
- [MEDIUM] tests/CatEcommerce.IntegrationTests/Endpoints/InventoryDatabaseFactsTests.cs:15-17 — this test bypasses the new catecommerce_dev guard. It reads CATECOMMERCE_TEST_DB directly and falls back to `Database=catecommerce_dev`. With the variable unset it creates and drops scratch schemas (DDL) on the shared dev database. `InventoryApiFactory.RequireBranchDatabase()` is meant to prevent exactly that (memory rule: unmerged-migration branches never test on catecommerce_dev). Remediation: use `InventoryApiFactory.RequireBranchDatabase()` here too.
- [MEDIUM] src/Infrastructure/CatEcommerce.Infrastructure/Inventory/EfStockLedger.Consumer.cs:221-227 — the controlled-drug correction does not verify its approver. `AdjustAsync` accepts `ApprovedByStaffId` from the calling context and checks only that it is non-null and differs from the caller. It does not check that the id is an active staff account holding `Stock.ApproveAdjustment` (OQ-21 is still open). Not exploitable until HO-PHM-001 calls the port, but a consumer that passes a request-body id would let a user name any colleague. Remediation: in the port, resolve the approver and require an active staff account with the approver role, or require HO-PHM-001 to pass an authenticated approval record.
- [LOW] src/Infrastructure/CatEcommerce.Infrastructure/Inventory/InventoryLedgerSql.cs:88-102 — the position guard is a convention, not a privilege. It trusts a session GUC (`inventory.ledger_apply`) that any connection can SET, and the app role owns the tables, so it can also DISABLE TRIGGER. This is fine as defence-in-depth against application bugs, but it is no barrier to a compromised connection. Remediation (later hardening): run the app as a non-owner role and make the apply function SECURITY DEFINER writing to a table the app role cannot write.
- [LOW] src/Infrastructure/CatEcommerce.Infrastructure/Inventory/InventoryLedgerSql.cs (fn_check_batch_usable) — location-kind quarantine is enforced only in C#. The usability trigger checks batch status and expiry, not location kind. Storage-breach quarantine (ADR-115) and customer returns move an Available batch to the Quarantine location, and only `StockLocationRules.Permits` stops a future consumer from consuming it there. Remediation: also refuse consuming kinds in the trigger when the location kind is Quarantine.
- [LOW] src/Infrastructure/CatEcommerce.Infrastructure/Inventory/EfStockLedger.Consumer.cs:165 — returns have no quantity cap. `ReceiveReturnAsync` checks that the party received the batch, but not that the returned quantity is at most the quantity received less earlier returns, so a consumer can inflate quarantine stock. Remediation: cap the quantity at consumed minus returned for (batch, party).
- [LOW] src/Application/CatEcommerce.Application/CommandHandlers/Validators/ConsignmentCommandValidators.cs:111 — `StorageKey` is client-supplied. Today documents are metadata only, so there is no impact. When a download endpoint is added it must not trust this key (IDOR or path traversal). Remediation: issue storage keys server-side when the file is uploaded.
