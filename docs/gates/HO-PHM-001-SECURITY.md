- [MEDIUM] src/Api/CatEcommerce.Api/Controllers/StaffPharmacyController.cs:53 (also :28 GetQueue; StaffControlledDrugsController.cs:32 GetRegister, :54 GetEntry): NFR-SEC-8 / OQ-12 as adopted in the Amended (build) row (8) says id-routed clinical reads write an access row through `TryLogClinicalAccessAsync`. `GET /api/staff/prescriptions/{id}/dispense-plan` is id-routed and returns the prescription and the cat header, but writes no clinical-access row. The queue (cat, customer, medicine per branch) and the register list and entry reads (catName, customerName, doseText) are not logged either. Prescription detail, dispensing detail, the cat and visit lists and the owner detail ARE logged and fail closed. Effect: a staff member with `Dispensing.Dispense` can read any prescription and its cat through the plan route and leave no access trail. Authorisation itself is correct; only the logging is missing. Fix: call `TryLogClinicalAccessAsync(…, plan.CatId, prescriptionId)` after the read and fail closed, the same way `GetPrescription` does. Decide with the owner whether the register and queue reads count as clinical-record access. -> backlog PHM.
- [LOW] src/Infrastructure/CatEcommerce.Infrastructure/Pharmacy/StaffWitnessVerifier.cs:57-82: the verifier returns the same generic result and makes one Argon2 call on every path. But the wrong-password path also does a staff-account UPDATE (`RecordFailedLogin`, line 77), which the unknown, locked and no-password paths do not. The extra database round trip is a small timing signal that tells a caller which identifiers are real, unlocked staff accounts. Low impact: the caller must already be signed in as staff, is limited to 10 calls a minute, and colleagues' identifiers are not secret. Fix: accept it, or make the failure paths do the same amount of work. -> backlog PHM.
- [LOW] src/Shared/CatEcommerce.Shared/Common/Helpers/ControlledDrugEntryCanonicalForm.cs:67-71 / ADR-145: the chain uses plain SHA-256 with no key and no copy of the tip held outside the database. Anyone who can get past the PH001 triggers (a database superuser) can also rebuild every seal from the altered entry onward, or delete the newest entries and seals together, and `verification` will still report `isIntact: true`. The only outside reference is an exported CSV someone kept. This is a limit of the design as specified, not a coding error. Fix: periodically write the per-branch tip `(chainPosition, entryHash)` somewhere outside the database (the off-site log, an emailed digest, or a signed export), or use HMAC with a key the database role cannot read. -> backlog PHM.

(3) Row triggers (UPDATE/DELETE) and statement triggers (TRUNCATE) on both tables raise SQLSTATE PH001, which is deliberately left unmapped so it surfaces as a 500. I-D1, I-D2 and I-D7 pass. The trigger SQL is built only from constants. Verification recomputes every seal and catches a missing entry, a wrong position, a wrong previous hash and an altered field. Free-text fields refuse control characters, so U+001F cannot be injected into the canonical form.
