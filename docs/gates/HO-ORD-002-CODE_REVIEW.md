- [HIGH] web/components/orders/StaffOrderQueue.tsx:45-46 (+ web/lib/api/staff-orders.ts StaffOrderFilters) — the "Placed from" / "Placed to" inputs are type="date" and the bare yyyy-MM-dd string is sent as `from` / `to`. The backend binds them as DateTimeOffset? (StaffOrdersController.cs:118-131) and filters PlacedOn >= from / PlacedOn <= to (StaffOrderQueryHandlers.cs:30-31). A date-only value binds as midnight in the server's zone (UTC), so `to` = 00:00 UTC of the chosen day: every order placed on the "to" day is excluded (a "12 Oct to 12 Oct" or "today" filter returns nothing), and `from` = 06:00 Dhaka, dropping 00:00-06:00 orders. This is the UTC-date assumption class the owner flagged. The mock (mocks/handlers/ordering/staff.ts:362) compares Date.parse(placedOn) >= Date.parse(from) the same way, so no test can see it. Fix: convert in the query hook with the branch zone: from = branchLocalToInstant(`${from}T00:00`, zone); to = the next day's 00:00 in the branch zone minus 1 ms (or T23:59:59.999), using useBranchTimeZone(); add a test that selects one day and asserts the two instants sent are 18:00Z of the previous day and 17:59:59.999Z of the day.
- [MEDIUM] web/components/checkout/CheckoutScreen.tsx:173-177 — RequestInProgress (409) sets inProgress = true and nothing ever clears it, so Place order stays disabled with "This order is already being placed." until the customer reloads; the cart still shows and there is no link to the order. The test "a 409 RequestInProgress ... disables Place order" (checkout.test.tsx ~L413) pins the dead end. Fix: after the me/orders invalidation, poll or re-check (or offer "Check my orders"), clear inProgress when the original attempt settles, and do not renew the key (the same key will replay the result).
- [MEDIUM] web/components/checkout/CheckoutScreen.tsx:178-196 — PolicyAcceptanceRequired / PrescriptionCatRequired set an error string only; the ['checkout','quote'] query is not invalidated, so the quote still has no pendingPolicies and the policies panel shows nothing to accept. Combined with the next item the customer has no in-page way forward. Fix: invalidate the quote on both codes (as is done for CheckoutQuoteChanged).
- [MEDIUM] web/lib/hooks/useIdempotencyKey.ts + CheckoutScreen.tsx:158-169, PosScreen.tsx:96-103 — the key is kept for an unchanged payload after ANY failure, but IdempotencyFilter stores and replays every 2xx-4xx response (IdempotencyFilter.cs: status >= 200 and < 500 goes to CompleteAsync). So after a definitive refusal whose cause is outside the payload (policy accepted, batch restocked, customer reactivated, payment method re-enabled, delivery tax configured) a retry with the identical body replays the stored refusal for as long as the key lives. The checkout fingerprint does not include pending policies (CheckoutPricing.cs:228-251), so accepting a policy and pressing Place order again replays the 400. Only a 422 renews the key today. Fix: renew the key on every response that carried a body (any ApiValidationError / ApiConflictError other than RequestInProgress); keep it only for network errors, 5xx and 409 RequestInProgress. Add a test: refuse once, change state, retry, assert a different Idempotency-Key.
- [MEDIUM] web/components/pos/PosScanField.tsx:30-42 + web/lib/hooks/useScanner.ts — the scan buffer is the input's own text and is only cleared after the async lookup resolves. A second scan arriving during the first lookup (normal cashier pace) is appended to the first barcode (a concatenated, unknown code) or wiped by scanner.clear() when the first lookup returns, so an item is silently dropped or an "unknown barcode" message appears. addSku also reads `lines` from the render closure that existed at keydown, so two quick scans of the same SKU can set the same quantity. Fix: clear the field synchronously on Enter (keep the text only for the failure announcement), serialise lookups in a queue, and use the functional setLines form to increment. Add a test that fires two scans before the first lookup resolves.
- [MEDIUM] web/components/pos/PosScreen.tsx:200 — onReview={() => { if (ready || lines.length > 0) ... }} is equivalent to lines.length > 0 (ready implies lines), so Enter in the amount field opens the review even with no customer name/mobile, a missing cat for a prescription line, a quote that says canSell: false, or a quote still fetching (isPlaceholderData is not part of `ready`; only the 300 ms debounce is). The dialog then shows the previous quote's total (reviewText uses quote.data, which is keepPreviousData) and its Complete sale button is not gated. The server refuses, so no wrong sale is recorded, but the keyboard path is the primary one and the review can state a stale total. Fix: gate onReview on ready && !quote.isFetching && !quote.isPlaceholderData; show the blocking reasons inside the dialog; add a test for Enter with an empty customer.
- [MEDIUM] web/components/orders/TransferCountdown.tsx:35-41 and web/lib/hooks/useMyOrders.ts useRefreshMyOrder — the expiry refetch fires once at the deadline. Cancellation is done by the server after the deadline, so the refetch can legitimately still return PendingPayment; the page then says "the time has passed" with live transfer instructions and never asks again (the expiredNotified ref blocks a second call). Fix: after expiry, refetchInterval of ~10-15 s (stop when status leaves PendingPayment or after a few minutes), and word the state as "we are checking" until the server answers. Add a test where the first refetch still returns PendingPayment.
