- [MEDIUM] web/components/files/FileUploader.tsx:164-172 — the Retry button for a queued row carries no per-file accessible name (`<RotateCcw/>Retry` only), unlike the adjacent Cancel/Remove button on the same row which does (`aria-label={`${…} ${item.file.name}`}`, line 179). Because uploads run sequentially (ADR-FE-150) while multiple *finished* rows can independently sit in `error` state at once, a queue with two or more retryable failures renders two or more controls with the identical accessible name "Retry" — a screen-reader or voice-control user cannot tell them apart. Not caught by C9/`files-a11y.spec.ts`, which only ever drives one row into the `error` state at a time. Fix: `aria-label={`Retry ${item.file.name}`}`, matching the Cancel/Remove button's own pattern.
- [MEDIUM] web/components/files/FileUploader.tsx:70-79 (`handleFiles`/`handleDrop`) and web/lib/hooks/useFileUpload.ts:213-245 (`addFiles`) — `multiple={false}` only limits the native file-picker dialog (the `<input multiple>` attribute); the drag-and-drop path is not restricted by it at all. `handleDrop` passes `event.dataTransfer.files` straight to `handleFiles` → `addFiles`, which queues every dropped file regardless of `multiple`. A host that sets `multiple={false}` for a single-file purpose (e.g. a future `CatProfilePhoto` consumer) can still have a user drop five files at once and get five queued uploads. No test (component or e2e) exercises drag-and-drop with `multiple={false}`. Fix: in `handleFiles`, when `multiple` is false, take only the first dropped/selected file (or show a rejection message for the rest) before calling `addFiles`.
- [MEDIUM] web/components/files/MediaViewer.tsx:51-56 and :82-86 — both the file-identity effect and the proactive `urlExpiresOn` refresh effect run on every render of `<MediaViewer>` itself, not gated on the `open` prop. The component's own doc comment (line 17-18) invites a host to "keep this mounted once and just flip `file`/`open` together" — but nothing requires the host to also clear `file` back to `null` when closing (the handover's own harness, `HarnessContent.tsx`, does exactly this: `viewerFile` is set on open and never reset on close). In that shape, once the dialog is closed, the still-set `current.urlExpiresOn` will eventually pass and the proactive effect will silently call the host's `onRefresh` for content that is no longer visible — a wasted round trip the host has no reason to expect from a closed dialog. Fix: gate both effects on `open` (e.g. `if (!open || !current) return;`), matching what a hidden `<FileThumb>` genuinely wants (always-relevant) versus a closed `<MediaViewer>` (not currently shown).
- [LOW] web/lib/api/files.ts:301-310 / web/lib/hooks/useFileUpload.ts:163-171 — `FileUploadRateLimitedError.retryAfterSeconds` is parsed from the `Retry-After` header but then discarded: the hook maps it to the same generic `NetworkFailure` code as every other transport failure, offers immediate manual Retry, and never surfaces the wait time. A user who retries right away can hit the same rate limit again. Not required by OQ-2 ("manual retry only"), but the parsed value is otherwise dead code. Consider surfacing it in the row's error message or disabling Retry until it elapses.
