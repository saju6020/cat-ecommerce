Every Billing action carries `[RequireAction]`, and the roles match the §12.3 table exactly (ActionRoles.Billing.cs): Approve and Reverse are Accountant and Admin only; CashUp.Close is Accountant and Admin only; CreditNotes and Refunds are ShopManager, Accountant and Admin. No `[AllowAnonymous]`.
- Branch scoping. Staff routes resolve `X-Branch-Id` through HttpContextActiveBranchAccessor (refused, never downgraded). Every by-id read and write compares `aggregate.BranchId` with the active branch and answers 404. This covers invoices, credit notes and their PDFs, payments, receipts, refunds, charges, cash-ups, COD, statements, matches and loyalty redemption. The one exception is the accounting export (M1).
- Customer portal. `[RequireCustomerSession]` is applied and the caller id comes from the session. Invoices and PDFs filter to non-Draft and non-Discarded and to the caller plus customers merged into the caller. Payments filter to Accepted or Reversed and the same customer set. A foreign id gets 404.
- Segregation of duties. RecordedBy is the caller and cannot be set from the body. Approve and Reject refuse the recorder (PaymentAggregate.Approve/Reject). Allocate, refund and reverse all require Accepted, so a pending payment cannot be used before approval.
- Over-refund and over-credit, including under concurrency. Payment.Allocate and RecordRefund check Unallocated. CreditNote checks the remaining amount per line and in total. Every mutation calls UpdateVersion, so the payment or invoice row is UPDATEd and the xmin token rejects a concurrent second writer. Owned allocation rows cannot slip past the token.
- Idempotency. Pre-checks and the unique indexes are keyed on (recorded_by / caller, key). BillingIdempotencyReplayFilter looks up by the current caller only, so it cannot replay another user's response.
- Gapless numbering. The series row is taken and committed in the same save, guarded by xmin. The retry reloads only the series row and detaches stale audit and message rows. ix_invoice_number and ix_invoice_sequence are not mapped by the filter.
- Triggers. invoice, invoice_line, payment, allocation entries, credit notes and lines, refund, COD, statement, statement line, bank_match, export run and loyalty_entry are append-only or immutable. charge, series, profile and loyalty_account refuse DELETE, and a closed cash-up is terminal. Status literals come from Enumeration.Value, and table names come from code constants. RawInsert and the receipt `nextval` are parameterised, with identifiers taken from the EF model, so there is no SQL injection.
- Statement CSV. The file is parsed in memory. Limits: 1 MiB, 5,000 rows, `[RequestSizeLimit]` of 2 MiB on that action only, strict UTF-8, row-numbered errors that never echo cell content, formulas kept as text, and the file name passed through Path.GetFileName and truncated. Descriptions and references are masked by CardNumberGuard before storage.
- CSV exports (list exports and the accounting ZIP). BillingCsv quotes every text cell and adds a leading `'` when the first significant character is `= + - @`, after leading tab, CR, LF or space (ADR-051).
- PDF. QuestPDF Community licence (already set by CatProfilesModule). There are only text spans, with no hyperlinks or images built from data. Responses send `Cache-Control: no-store`.
- Logging. The only new log calls carry ids, error codes and exception type names. There is no EnableSensitiveDataLogging and no HTTP body logging. Validation errors never echo the attempted value.
- C-ALL-2 eraser. BillingPersonalDataEraser changes nothing and reports Held under D-9. That is consistent with the Financial/Forbidden classification.

- [HIGH] src/Domain/CatEcommerce.Domain/Aggregates/Billing/PaymentAggregate.cs:177-182 (Reject), :233-235 (ReleaseEarmark), :262-281 (Reverse); CreditNoteAggregate.cs:49-69 (Reason); CashUpAggregate.cs:~58-64 (Explanation); BankMatchAggregate.cs:51-61 (UnmatchReason). These fields reach src/Application/CatEcommerce.Application/DomainEventHandlers/Billing/AuditBillingDecisionHandler.cs:43, 49, 55, 61, 73 and 80.
  - **Rule broken.** C-5 and §19 gate 2 require the card-number guard on every free-text money field. §20.6 says no card number may appear in a column or an audit row.
  - **What the code does.** These reasons and explanations are stored as written. They are also copied verbatim into `AuditEntry.AfterValue`, and the HO-ACC-001 interceptor adds them to its change snapshot. None of them calls CardNumberGuard. Only payment reference and notes, refund reference and reason, and the COD reference are guarded.
  - **Exploit scenario.** An Accountant reverses a double-charged card payment with the reason "card 4111 1111 1111 1111 charged twice at terminal". The full PAN is now in billing.payment.reversal_reason and in two audit rows. All of these are Forbidden-to-delete under D-9, so the PAN cannot be removed without breaking the immutability triggers. The same applies to a credit-note reason or a cash-up variance explanation.
  - **Fix.** Call `CardNumberGuard.LooksLikeCardNumber` and throw `ReferenceLooksLikeCardNumber` in RequireReason (payment), CreditNote.Issue, CashUp.Count, BankMatch.Unmatch and Charge.Void. Do the same for the remaining free-text fields: invoice Notes (InvoiceAggregate.ValidatedNotes), the earmark Label (which is also sent to the customer in the payment-received message), the manual charge Description and the corrected-draft line Description. Add one unit case per field, plus an I-X1-style assertion that no audit row contains a Luhn-valid run.
- [MEDIUM] src/Shared/CatEcommerce.Shared/Common/Helpers/CardNumberGuard.cs:20 — separator bypass of the guard and the mask.
  - **The gap.** The digit-run regex `\d(?:[ -]?\d)*` accepts only a single space or dash between groups. §8.8.2 says to "strip spaces and dashes".
  - **Probe results (scratch harness).** These are NOT detected or masked: `4111  1111  1111  1111` (double space), `4111 - 1111 - 1111 - 1111`, tab-separated, NBSP-separated (typical of copy-paste from PDFs and web pages), `4111.1111.1111.1111`, `4111/1111/...`, `4111_1111_...`, and Bengali-digit `৪১১১ ১১১১ ১১১১ ১১১১`. Bengali digits get past because `char.IsDigit` and `\d` accept them, and `PassesLuhn` then computes `c - '0'` on non-ASCII digits. A PAN with a stray digit glued on (`94111111111111111`) is also missed. The developer's `ref 9 4111 1111 1111 1111` fix holds.
  - **Fix.** Normalise before matching: map Unicode decimal digits to ASCII with `char.GetNumericValue`, and treat any run of whitespace, `-`, `.`, `/` or `_` as a separator. Keep the whole-group window logic. Use the same normalisation in MaskCardNumbers.
- [MEDIUM] src/Domain/CatEcommerce.Domain/Aggregates/Billing/BankStatementAggregate.cs:~73-75 — masking gaps on statement lines.
  - `BankTransactionId` is stored without `Mask()`.
  - Reference and Description are truncated before they are masked, so a PAN that straddles the 100- or 500-character cut is stored as an unmasked 13-15 digit prefix.
  - **Fix.** Mask first, then truncate, and mask BankTransactionId as well.
- [MEDIUM] src/Api/CatEcommerce.Api/Controllers/StaffAccountingExportsController.cs:33-60 and src/Read/CatEcommerce.Read/QueryHandlers/Billing/AccountingExportQueryHandlers.cs:28-120 — the export bypasses branch assignment.

- [MEDIUM] src/Application/CatEcommerce.Application/DomainEventHandlers/Billing/LoyaltyEventHandlers.cs:97-101 together with src/Infrastructure/CatEcommerce.Infrastructure/Persistence/Configurations/LoyaltyConfiguration.cs:44-45 — the second credit note on a paid invoice never claws points back.
  - **Cause.** An AccrualReversal entry carries both invoice_id and credit_note_id, and it is `idempotent_source`. That makes `ix_loyalty_entry_kind_invoice` (kind, invoice_id) unique. The first partial credit note posts its reversal. A second credit note on the same invoice collides on that index.
  - **Effect.** The reversal handler throws after the credit note has already committed: a 500 to the caller, and the points are never taken back. When loyalty is enabled, a customer can return goods in two steps and keep the points for the second return. (The same collision blocks a legitimate second clawback.)
  - **Fix.** Make the idempotency key for AccrualReversal the credit note alone, for example by excluding AccrualReversal from the (kind, invoice_id) index filter. Add an integration case with two partial credit notes.
