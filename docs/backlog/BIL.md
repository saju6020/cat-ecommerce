# Backlog — Billing and payments (HO-BIL-001)

Medium/low findings not blocking the merge (owner rule 2026-09-27: only BLOCKER/HIGH block a gate).
Fix in a later batch. Source: `docs/gates/HO-BIL-001-*.md` and `docs/test-cases/TC-HO-BIL-001.md`. Merged at
`0442f9ff`; all five gates PASS. Round 1 failed ARCHITECTURE (two HIGHs: the read side materialised aggregates, and the
loyalty merge transfer was committed in two saves) and SECURITY (one HIGH: no card-number guard on the free-text money
fields that are copied into audit rows); the combined follow-up review (`HO-BIL-001-REVIEW-R2.md`) closed all three.
Those HIGHs are not listed again below. Phase J (the visit, dispense and surgery item sources) is deferred by owner
decision and is not a failure (row 32).

Findings raised by more than one gate are one row, with every source listed. Gate finding ids: `SECURITY M3`,
`ACCEPTANCE L3` and so on are the finding's position within that gate's MEDIUM or LOW list (every BIL gate lists them
unnumbered, so the id is the order of appearance; `ACCEPTANCE M1` is its single MEDIUM). ARCHITECTURE findings that the
gate ties to a developer-declared deviation also carry `(deviation n)`, which is unambiguous; `F-n` are the TEST gate's
own backlog ids and `XU-n` / `XI-n` its probe rows in the TC sheet. Three tags matter: **Owner decision** rows cannot
be fixed until the owner rules; **Next fix** rows are the follow-ups the integrator called out at the merge;
**Integrator** rows are work only the integrator can do. Rows already closed by the follow-up rounds, the later fix
commits or this paperwork are marked **Closed** and kept so the same finding is not re-raised.

The card-number guard (`CardNumberGuard.cs`, SRS C-5) produced most of this list. Its settled behaviour, so the rows
below read correctly: detection is boolean and refuses a value; masking is the separate path used only where a value
must be stored as received (bank-statement Reference, Description and BankTransactionId, and the statement
`SourceFileName`). Two exemptions narrow handover §8.8.2's literal "13 to 19 digits passing Luhn": a Bangladeshi mobile
number with its country code (`^8801[3-9]\d{8}$`, a 13-digit window only) and the system's own `INV-` / `CN-` document
numbers. Letters between digit groups deliberately do not join them. Bank account, tax registration and routing numbers
are deliberately unguarded (§11.4 C1; a 13-digit tax or routing number would be refused about one time in ten).
